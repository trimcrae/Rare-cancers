# Tests known to FAIL in the dev sandbox because a scientific dependency is absent.
#
# ⛔ THIS FILE EXISTS BECAUSE A COUNT LET A REAL FAILURE THROUGH (2026-08-08). The pytest gate in
# scripts/preflight.sh tolerated a NUMBER of sandbox failures and asserted they were "all dep-related"
# without checking. A genuine regression -- test_lint_citations.py::test_the_ledger_does_not_anchor_itself,
# broken by a newly committed artifact -- took the count from 48 to 49, sat under the baseline of 50, and
# the gate printed PREFLIGHT OK. That tree was pushed and turned `main` red. CI with full deps reported
# exactly one failure against 7,363 passes, so nothing about the failure was ambiguous; the local gate
# simply could not see it. preflight.sh's own comments had already recorded the limitation in words --
# "This script stores no baseline LIST, only a COUNT, so the excess cannot be identified here" -- which is
# why the fix is a list and not a bigger number.
#
# ⚠ THIS IS NOT AN IGNORE LIST. An ignore list suppresses; this one NAMES what is tolerated, fails the
# build on anything absent from it, and reports entries that have started passing so the list shrinks.
# A test may only be added here after its failure is traced to a missing module IN THIS SANDBOX -- not
# because it is inconvenient. Every entry below was traced on 2026-08-08: all are ModuleNotFoundError for
# rdkit, boto3 or numpy, including test_vast_machine_blacklist.py::test_clear_requires_snapshot, whose
# AssertionError is a subprocess exit code that differs only because boto3 is missing inside it.
#
# Regenerate deliberately, in a commit, when the sandbox's installed packages change:
#   python3 -m pytest research/modalities/tests/ -q --continue-on-collection-errors \
#     --ignore=research/modalities/tests/test_ternary_endpoint_align.py \
#   | grep '^FAILED' | sed 's/^FAILED //; s/ - .*//' | sort > research/modalities/tests/sandbox-failure-baseline.txt
#   (then re-add this header)
#
# 5 further modules cannot be IMPORTED here and are counted separately by the gate, not listed here.
#
# ⭐ UPDATED 2026-08-09, AND THE UPDATE IS IN BOTH DIRECTIONS — WHICH IS THE POINT OF A LIST.
# The sandbox's package set moved: numpy is now importable here, so 9 entries stopped failing and
# were PRUNED (test_congeneric_fanout seed tests, test_nr4a3_5bt, test_nrv04_pe_stage_probe,
# test_selcal_stage). In the same pass 14 entries were ADDED, each traced to a module before being
# written down, not assumed:
#   * 11 in test_abfe_diagnostics.py -> ModuleNotFoundError: No module named 'pymbar'
#     (research/modalities/nr4a3_abfe.py:69 and :683)
#   * 3 in test_slow_cv.py           -> ModuleNotFoundError: No module named 'scipy'
#     (research/modalities/nr4a3_slow_cv.py:114)
# ⚠ These 14 did not appear in the 2026-08-08 baseline because they were then failing for the
# numpy gap and were among the entries that gap already covered; with numpy present, the NEXT
# missing import is what they now stop on. A dependency gap that moves is not a gap that closed.
#
# ⭐ PRUNED AGAIN 2026-08-15, AND IT IS THE SAME NINE ENTRIES THE 2026-08-09 NOTE ABOVE ALREADY
# SAYS WERE PRUNED. They were back in the file, so something re-introduced them — a merge that took
# this side of a conflict, most likely, since nothing else writes here. The gate reported them as
# "9 baseline entr(y/ies) no longer fail" on a run measuring 57 failures, 53 of which were listed
# here; removing exactly these nine leaves the list at 53 and the two numbers agree.
# ⚠ THE LESSON IS ABOUT DIRECTION, NOT ABOUT THESE NINE. Pruning is always safe: a pruned entry that
# starts failing again fails the build loudly. A stale entry is the dangerous one — it is a standing
# licence for a test to fail, and this file exists because exactly that licence let a real regression
# through. A resurrected entry is invisible unless the gate's "no longer fail" line is acted on, so
# act on it every time rather than reading past it.
#
# ⛔⛔ UPDATED 2026-08-12, AND IT REVERSES THE 2026-08-09 PRUNE EXACTLY — WHICH IS THE FINDING, NOT
# THE FIX. The 9 entries pruned above on the grounds that "numpy is now importable here" were
# re-added today, because in THIS container numpy is NOT importable:
#   `python3 -c "import numpy"` -> ModuleNotFoundError. Traced per file before re-adding, never
#   assumed: test_selcal_stage -> selcal_stage.py:335 (numpy); test_nrv04_pe_stage_probe ->
#   test_nrv04_pe_stage_probe.py:315/343/356 (numpy); test_nr4a3_5bt -> nr4a3_5bt_assemble.py:398
#   (numpy) and :453 (rdkit); test_congeneric_fanout -> test_congeneric_fanout.py:1671/1705
#   (numpy, boto3).
# ⚠ THE MECHANISM ASSUMES A STABLE SANDBOX AND THE SANDBOX IS NOT STABLE. This file is a per-
#   CONTAINER fact being stored as a per-REPOSITORY one, so it oscillates: the same 9 tests were
#   pruned on the 9th and re-added on the 12th with no code change between, and each flip fails a
#   preflight for someone. That is a cost worth naming rather than quietly paying every time.
#   It does NOT make the list wrong — a list that names what is tolerated still beats a count that
#   hides it, which is why this file exists (2026-08-08 incident above). What it means is that a
#   red pytest gate whose named failures are all ModuleNotFoundError is a statement about the
#   container, and the FIRST diagnostic is `python3 -c "import numpy"`, not a hunt through the diff.
#   ⭐ The 14 pymbar/scipy entries added on the 9th are DELIBERATELY LEFT IN PLACE: today they do not
#   fail, they fail to be COLLECTED (numpy is missing upstream of pymbar), and the gate counts a
#   collection error separately. Pruning them would only guarantee re-adding them next container.
